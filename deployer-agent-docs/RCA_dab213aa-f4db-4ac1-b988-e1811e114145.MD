# RCA — Admin "Revoke/Delete gift license" does nothing in production

**Deployment:** cinema-hub-402 (obsidiancinema.com / www.obsidiancinema.com)
**Active run:** dab213aa-f4db-4ac1-b988-e1811e114145 (redeploy, success, frontend_type=cloudflare)
**Symptom:** On /admin → Licenses, the confirm dialog opens, but pressing **Confirm** for Revoke/Delete changes nothing; the row remains after refresh.

## Verdict
The admin mutation requests **reach the production backend and are rejected with HTTP 401 Unauthorized**. The `session_token` cookie the browser presents does not match a live session, so the delete/revoke never executes. This is an **auth/session** problem, not a frontend-build, CORS, data-shape, or 404 key-mismatch problem.

## Evidence
1. **Production bundle is the latest build (not stale).** Fetched the live JS `https://cinema-hub-402.emergent.host/static/js/main.db6c0107.js` and confirmed it contains the new code: `delete-license-`, `revoke-`, `Permanently Delete License`, `AlertDialog`, `Reset Machine Lock`. `index.html` is served `Cache-Control: no-cache, no-store, must-revalidate`; no service worker in source. So the dialog-open fix is genuinely live.

2. **The POST arrives and returns 401 (preflight is fine).** Production backend access logs (run dab213aa):
   ```
   OPTIONS /api/admin/licenses/delete  -> 200 OK      (CORS preflight OK)
   POST    /api/admin/licenses/delete  -> 401 Unauthorized
   GET     /api/admin/licenses         -> 401 Unauthorized
   ```

3. **401 means "no valid session", not a role problem.** In `backend/server.py`:
   - `require_admin()` → calls `require_user()`; raises **403** ("Admin access required") only for an authenticated non-admin.
   - `require_user()` raises **401** ("Not authenticated") when `get_current_user()` returns `None`, i.e. the `session_token` cookie is missing OR not found in `user_sessions` OR expired.
   The observed status is **401**, so the admin check was never reached — the cookie did not resolve to a live session.

4. **Backend holds exactly ONE valid admin session; the browser cookie is stale.** `user_sessions` for the admin (`user_id=user_c709f5461327`, email billrules@gmail.com) contains a single doc, created `2026-10-27T02:16:40Z`, expires `2026-11-03` (not expired). Because the browser still gets 401, its cookie holds a *different* (already-deleted) `session_token`.

5. **Design cause — single-session-per-user wipe.** `POST /api/auth/session` runs:
   ```python
   await db.user_sessions.delete_many({"user_id": user_id})
   await db.user_sessions.insert_one(session_doc)
   ```
   Every login deletes ALL prior sessions for that user. So any second authentication for billrules@gmail.com — a second tab, the apex vs `www` variant of the site, or the Electron desktop client — silently invalidates the session the admin's active tab is using. That tab's cookie then 401s on every call. Preview never hits this (a single login/session in play) — which is why it "works in preview."

6. **Amplifier — apex/www + host-only cookie.** The production JS hardcodes the API base to the apex: `"https://obsidiancinema.com" + "/api"`, while the site is also served on `www.obsidiancinema.com`. The session cookie is set `httponly, secure, samesite=none, path=/` with **no Domain attribute** (host-only). Cross-site XHR still carries it via SameSite=None, so this is not the direct 401 trigger, but logging in across apex and `www` multiplies the single-session invalidation in (5).

7. **UX amplifier.** `doAction()` on the admin page catches the 401 and only shows a generic `toast.error(...)` and does **not** refetch or force re-login — so to the user it looks like "Confirm did nothing."

## Explicitly ruled out
- **Stale/cached build or failed deploy** — latest bundle is live; latest run succeeded (all steps green); index.html is no-cache.
- **CORS/SameSite block** — OPTIONS preflight returns 200; cookie is SameSite=None/Secure; an earlier `POST /api/admin/licenses/gift` succeeded (200) with the same mechanism.
- **404 "License key not found" / key-shape mismatch** — status is 401, so `delete_one`/`update_one` was never reached. For completeness, production gift docs are well-formed: each has a `license_key`, `gift:true`, and `created_at` stored as an ISO string (the same shape that works in preview). `delete_one({"license_key": key})` / `update_one` would match fine.
- **"200 but row remains" / duplicate doc / cached GET** — not applicable; the request is rejected at auth (401) before any DB write.

## Fixes
**User (immediate, verify):** In the exact browser/tab being used, log out and log back in on ONE canonical domain (pick apex `obsidiancinema.com` or `www` and use it consistently), then in DevTools → Network confirm `POST /api/admin/licenses/delete` sends the `session_token` cookie and returns 200. Avoid being logged in simultaneously elsewhere (other tabs/devices or the desktop app), since each login invalidates the others.

**Code (E1, requires redeploy):**
1. Stop wiping all sessions on login — remove/relax `db.user_sessions.delete_many({"user_id": user_id})` in `POST /api/auth/session` (support concurrent sessions, e.g. keyed per device) so one login no longer logs out the others.
2. Set the session cookie `Domain=.obsidiancinema.com` so apex and `www` share a single cookie, and/or canonicalize to one host (redirect `www`→apex to match the hardcoded `REACT_APP_BACKEND_URL=https://obsidiancinema.com`).
3. Handle 401 in the admin UI (and globally) — prompt re-login instead of a silent generic toast, and surface the failure clearly.
